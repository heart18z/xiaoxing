# 图片上传与多模态上下文修复（APP 123）

## 原因
- APP 选图强制使用原图，并在上传前拦截超过 8MB 的图片。
- 上传时已经进行多模态解析，但正式对话只接收解析文字，没有接收原始图像内容。
- 后续聊天拼接历史时忽略附件 payload，导致“把这些安排给某人”丢失图片上下文。
- 已发送消息只渲染附件文件名。

## 调整
- 手机选图使用系统压缩结果；长边超过 3200 或超过 8MB 时进一步压缩，上传前检查账号仍一致。服务端保留 20MB 文件上限，并使用 ImageIO 采样读取大照片后生成有界 JPEG，避免完整解码超大原图。
- 同轮普通和流式对话都将实际 image_url 数据与用户要求一起发送。无新附件时可引用当前可见对话中最近 5 次用户发言里的最近一组附件；清空对话后不引用之前的图片。
- 历史消息保留经过归属校验的附件解析内容，作为引用资料；不让附件覆盖系统规则或当前用户要求。
- APP/网页消息展示图片缩略图。预览接口验证登录和文件归属；APP 点击请求较清晰图片。多附件文件名按请求 ID 顺序返回。
- APP versionCode 123。Android/iOS 需要重新打包安装，当前工作未生成签名安装包。

## 验证
- APP 静态检查、68 项单元测试通过。
- Android 资源编译、生成的 Kotlin 及原生实现编译通过；iOS 资源编译通过。Windows 未做 Xcode 链接或 iPhone 真机安装验证。
- Java 编译、Stage3FilesRegression、ImageContext123Regression、ChatContextRegression（包含 Stage1Regression）通过。
- 新测试验证 4800 万像素图片缩图、正确 MIME、普通/SSE 线上请求格式（本地模拟模型服务器）、后续引用、清空上下文、跨账号访问拒绝。
- Playwright 本地接口夹具验证两张图片显示、失败后重试、点击大图预览；没有发送真实聊天或创建事件。
- 网页生产构建通过。
- 用户更新后台名称后，重新读取配置并实测 `deepseek-v4.1-flash`：正确识别合成图片中的“9月24日 14:00 去客户现场”和“9月25日 10:30 提交9017号报告”，接收人均为陈一，约 16.6 秒。仅调用模型，无真实事件创建。旧名称 deepseek-v4-flash 的失败结果不代表新配置。
